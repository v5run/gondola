# Security audit and demo boundary

Date: 2026-11-07. Scope: source review of the local FastAPI application, agent tools, storage, integration adapters and configuration; targeted offline tests. This is not a penetration test, a comprehensive secret scan, a deployment assessment, or a guarantee of security. No real provider/merchant operation was performed in this audit. Use synthetic data only. For a threat-oriented explanation of the implemented demo controls and proposed production agent security, see [AI agent security](../strategy/AI_AGENT_SECURITY.md).

## Findings and actions

| Priority | Area | Observed and current state | Before real use |
|---|---|---|---|
| Critical | Authentication / exposure | API routes, including reads, mutable settings, approvals, model jobs and local data, have no user authentication, authorization or tenancy isolation. The standard `python -m gondola.api` entry point now refuses non-loopback binds, rejects untrusted Host headers and cross-origin unsafe browser requests, and blocks requests marked cross-site by Fetch Metadata. Exact additional Host names may be set in `GONDOLA_ADDITIONAL_HOSTS`; never use this to expose the unauthenticated demo. Direct ASGI server invocation can bypass the bind restriction; a local tunnel or proxy can still expose the service. CORS permits only local Vite origins, but these checks are **not** authentication or complete CSRF protection; requests without Origin remain allowed for local clients and webhooks. | Keep local and on a trusted machine; do not publicly expose the API. Build authenticated sessions, per-store RBAC, CSRF/origin protections, rate/resource limits and tenant isolation; test them. |
| Critical | External action approval | Previously a configured DoorDash credential could activate `AppPauseExecutor`; Square had write/seeding methods; background notification jobs could send once keys existed. They did not require authenticated, action-specific manager approval. Now DoorDash item writes raise, executor pauses are always dry runs even with injected clients, Square rejects non-read methods except the exact order-search POST, and the application notifier writes dry runs. These are code-level demo boundaries, not isolation from arbitrary Python. Low-level Twilio/SendGrid adapter functions can still send when called directly by trusted code. A valid inbound webhook returns a TwiML reply that Twilio may deliver; it is not a manager-approved notification workflow. | Before enabling *any* live merchant or notification operation, implement a separate privileged executor that requires an authenticated authorized manager's explicit, expiring, single-use approval bound to the exact store, action, parameters and state version; revalidate policy/consent, log identity and outcomes, ensure idempotency, read back results and provide revocation/kill switch. Reassess which routine notifications can be pre-authorized. Test bypasses, races and provider failures. There is no live approval implementation today. |
| High | Storage and secrets | `.env` is ignored; `.env.*` now ignored except `.env.example`. Configuration loads keys server-side. DuckDB `data/gondola.duckdb`, SQLite in `.local/` and `out/`, JSON, CSV, reports, logs and backups are **not encrypted by this application**; some synthetic fixtures and outputs are tracked. Ignoring files does not encrypt them. Reviewed provider failures and background job errors now use generic messages instead of raw exception bodies/tracebacks. Model inputs, tool traces and other logs can still contain sensitive data and are not comprehensively scrubbed. | Do not place customer data or production keys in this demo. Use OS/volume or managed DB encryption including backups and journals, managed key rotation and least-privilege secrets, private filesystem permissions, retention/deletion policy, and secret scanning of current files **and Git history**. Rotate any exposed credential, not just remove it. Redact and limit logs. |
| High | Communications and data sharing | REST provider URLs reviewed use HTTPS and default certificate verification. Local Uvicorn is plain HTTP; TLS termination, trusted proxy configuration and service-to-service security are not provided. SMS/email are not end-to-end encrypted. A configured model sends prompts and tool data to the provider; provider retention/training terms and access control were not verified. | Use HTTPS with a trusted TLS endpoint and encrypted internal links where applicable; verify certificates, protect ingress and configure trusted proxies. Minimize/authorize data sent to providers, review retention and contracts; use no real data in the demo. Avoid sensitive SMS/email content. |
| High | Agents and prompt injection | ADK agents execute in the application process, **not** in a container/VM or OS sandbox; they inherit the process's environment and permissions. Tool lists are narrower than general shell access: Rush tools use simulated kitchen actions; Flex publishes proposals and acceptance rechecks resources; Order Manager selects a checked plan and version-rechecks before atomic local commit. Close agents primarily explain deterministic outputs; the numeric guardrail only checks numbers, not overall safety or truth. Instruction text is not an authorization boundary. Local traces are not tamper-proof. | Isolate agent workers from production credentials and filesystem; restrict network egress and use scoped tools/capabilities, resource limits and independent server-side policy checks. Treat all external/user content as untrusted. Add adversarial prompt-injection, data exfiltration and tool abuse tests; prevent secrets in prompts and outputs. Enforce live approvals outside the model. |
| High | Inbound SMS | Previously the API did not validate a Twilio signature despite a helper being present. When `TWILIO_AUTH_TOKEN` is set, it now requires a valid signature over the fixed HTTPS `PUBLIC_BASE_URL` and an `ALERT_SMS_TO` sender; duplicate parameters and query strings are rejected. Without a token, the local mock route remains unauthenticated. | Keep private. Validate provider webhook behavior and replay handling with real integration tests, add rate limiting and robust identity/opt-out handling; a signed phone number alone is not strong manager authentication. |
| High | PDF browser | The report renderer previously explicitly disabled the Chromium sandbox. It now requires the browser sandbox, disables JavaScript and blocks requests other than the report file. Sandbox support depends on the host; PDF rendering now fails rather than falling back to unsandboxed Chromium. The original audit unit-tested launch configuration; integration subsequently verified actual sandboxed PDF rendering on the demo machine, with JavaScript and a second local-file iframe blocked. This is a browser sandbox, **not** an agent sandbox. | Verify PDF rendering on the demo machine with its actual Chromium sandbox, and independently isolate any untrusted report content. |
| Medium | Static files | The SPA fallback now resolves paths and refuses files outside `web/dist`, including symlink escapes. | Continue to audit all file inputs and ensure runtime assets are not attacker-writable. |
| Medium | Dependencies | Python requirements have unbounded lower limits; no Python lock or vulnerability scan was established. The original npm lock reported 1 high and 3 moderate advisories. Vite was updated to 6.4.5 and React Router to 7.18.5; `npm audit --package-lock-only` now reports zero findings on 2026-11-07. This does not prove the dependencies are safe. | Pin/lock and audit Python and JS dependencies, triage and upgrade advisories, add automated scanning and review transitive dependencies. |

## Integration corrections and verification

Security hardening by v5run was integrated with two reviewed corrections: intentionally omitted books/stock/analyst steps on a closed day are identified explicitly, preserving `closed` status without exposing exception text; the SPA index fallback is resolved and checked against the distribution directory before serving. A genuine report failure on a closed day still produces `partial` status. Added regression coverage preserves both behaviors.

The real-symlink test explicitly skips WinError 1314 when Windows cannot create symlinks. A separate modeled path-resolution regression exercises the fallback check on this machine; it failed before the correction and passes afterward. This is not an end-to-end symlink exploit test on Windows. Run the real-symlink check on a capable CI host.

Independent checks on the integrated checkout: clean dependency install and production build passed (zero reported npm advisories), seven browser workflow pages plus navigation/admission/reload/redirect/mobile checks passed without JavaScript or HTTP errors, and an actual sandboxed Chromium PDF rendered while blocking JavaScript and a second benign local HTML file. The synthetic burst admitted 27 orders and declined 2. No real model, messaging or merchant call was made. Evidence: [integration checks](../demo/security-integration-checks.json). Full integrated offline suite: **268 passed, 1 skipped**, 252.22s. The skip is the unavailable Windows symlink privilege, with modeled containment coverage passing. Existing deprecation warnings remain. The refreshed local demo health/agent configuration and Host rejection were checked without requesting another model run.

## Original audit checks (historical)

- A simple pattern scan over 783 tracked working-tree files below 10 MB found no matches for five common Google/GitHub/AWS/SendGrid/private-key patterns. It did not scan history, ignored files, all secret formats, or the one larger file; no conclusion about absence of secrets is possible.
- Follow-up offline checks cover Host/origin/Fetch Metadata rejection, loopback entrypoint enforcement, generic provider/job errors and sandbox launch configuration. The integration, security, agent, Rush, Flex and Order Manager selection passed 123 tests before the final two added security checks; the security file alone then passed 13 tests. The security/integration/clock/Present selection passed 60 tests. The frontend production build passed after the major router upgrade, and `npm audit --package-lock-only` reported zero advisories; browser navigation and PDF rendering were not verified in this environment.
- Earlier offline tests cover configured DoorDash and Square write denial, injected Square executor denial, notifier dry runs with configured credentials, Twilio signed/unsigned/tampered/unauthorized requests, restrictive CORS and static symlink escape. `tests/test_integrations.py`, `tests/test_security_audit.py`, and `tests/test_agents.py`: 30 passed with model credentials disabled. Mocking verifies code paths, not provider security.
- Full suite first attempt: 236 passed, 5 failed, 17 errors. Early agent tests lacked the generated DuckDB file; PDF/report tests lacked a browser. Once the DB was created by app startup, targeted agent tests passed. No full clean suite or live provider test is claimed.

## Safe demo checklist

1. Run on a private, trusted computer on loopback, with only synthetic fixtures. Install Node 20+ for frontend rebuilds and verify sandboxed PDF generation on the actual demo machine. Do not use a public tunnel, production merchant credentials, real customer data or sensitive prompts.
2. Model credentials, if used, stay server-side and incur actual provider requests; use a limited test key and remove/rotate it after the event. Do not describe cloud model use as offline or sandboxed.
3. Show a local simulated decision, its checks and receipt; explain that the manager approval UI is only local demo state and cannot authorize a live write. Customer acceptance in Flex is also a local simulated interaction.
4. Present secure deployment, authenticated approvals and encrypted storage as **next steps**, not features already delivered. Disclose advance-built work and confirm Sandia track requirements with organizers.
