# Gondola: Can a third party pull the availability levers? (Nov 2026)

Confidence tags: **[doc]** = read on the official page this session. **[title]** = known only from a search-result title or URL, page not read. **[prior]** = background knowledge, not re-verified. Treat [title] and [prior] items as hypotheses to check.

## Verdict

- **No self-serve API lets a small third party write availability to DoorDash, Uber Eats or Grubhub today.** Every marketplace write API is gated by partner approval. DoorDash Marketplace says it is "not yet generally available" and the pipeline is "at capacity" [doc]. Uber needs an NDA/API licence and "may require written approval" [doc]. For Grubhub we found no public access path [doc/title].
- **The levers do exist technically**, though, and some are per-channel:
  - DoorDash: item `is_active` toggle and timed store deactivation [doc].
  - Uber: item `suspension_info.suspend_until`, plus store online/paused [doc].
  - Deliverect: per-channel busy mode with an added prep-time delay [doc].
- **Prep-time/busy mode is the weakest lever.** DoorDash documents only per-order `prep_time` at confirmation, with no store busy mode [doc]. Square's Busy Mode works for Uber Eats only, not DoorDash [doc].
- **Per-channel item hiding ("86 on DoorDash, keep for dine-in") cannot be automated through Square.** Square's per-item "Where it's sold → DoorDash/Uber Eats" toggle exists in the UI [doc], but `CatalogItem.channels` is read-only, and Square staff said in Nov 2023 and Apr 2025 that visibility can't be set programmatically [doc]. Inventory = 0 is all-channel, and DoorDash removes the item outright rather than showing it sold out [doc].
- **Per-channel quantity caps exist nowhere as a native field** (DoorDash/Uber/Square/Toast) [doc: absent from the DoorDash spec]. Gondola has to count sales per channel itself and fire an availability toggle at the cap.

**"One integration provider per store":** We found no explicit sentence either way. The evidence points to one provider per store:
- The store is configured with **a single** `provider_type` and `location_id` [doc].
- Changing provider type means asking a DoorDash rep [doc].
- Onboarding rejects with "This store is already live on the requested POS integration but using a different location_id" [doc].
- "DoorDash does not support having multiple stores sharing the same provider_type / location_id combination" [doc].

So if a restaurant's Square/Toast/Otter integration already owns the store, Gondola very likely cannot attach as a second Marketplace provider. Treat this as an inference, and confirm it with the DoorDash sponsor.

## Recommended path

**(a) 36-48h hackathon demo**
1. **Ask the DoorDash sponsor on day 1 for Marketplace sandbox access** (test store + JWT). If granted, the levers are real calls against a DoorDash test store:
   - per-item off: `items/status`
   - timed pause: `stores/{id}/status` + `duration_in_secs`
   - prep-time extension: per-order `prep_time` on confirm, using test orders
2. **Real Square sandbox adapter** (self-serve): Inventory API count → 0 sets `sold_out` for the "86 everywhere" case. This shows a real write and the real limitation.
3. **Policy engine is the product.** Build one `ChannelAdapter` interface (`set_item(channel, item, available, until)`, `pause(channel, secs)`, `add_prep(channel, mins)`) with per-channel counters for caps, plus a kitchen-load trigger.
4. **Mock (and say so on the slide):**
   - the incoming multi-channel order stream and kitchen-load signal
   - Uber/Grubhub/Deliverect adapters, recorded against documented request shapes
   - the DoorDash adapter, if sponsor access isn't granted
   - a fake customer storefront showing the item vanish

**(b) Pilot with an independent Pittsburgh restaurant**
1. **Ship "recommend + one-tap human action" first.** Gondola predicts a sell-out or overload and pushes an alert like "Pause brisket on DoorDash, 4 left for dine-in". The manager taps it in the DoorDash/Uber merchant app or tablet. This avoids third-party Merchant Portal access, and it works whatever POS they use.
2. **Automate where the restaurant's stack allows:**
   - Square: whole-store 86 via Inventory API (OAuth, self-serve). Not per-channel.
   - Deliverect customers: per-channel pause/prep delay via Store API, after partner certification.
   - Toast: Stock API only if certified for `stock:write`.
3. **Pick a pilot restaurant that already uses Deliverect or Otter** if possible. That middleware is the only place where per-channel busy/pause is exposed today [doc].
4. Apply in parallel to DoorDash Marketplace and Uber. Expect a long queue ("at capacity").

## Risks

- **Access risk is the main one.** Every direct marketplace write is approval-gated, and DoorDash says its pipeline is at capacity [doc].
- **Provider conflict:** with one `provider_type` per store, Gondola probably can't coexist with the restaurant's POS integration on DoorDash [inference].
- **Square inventory = 0 also 86s the item in POS/dine-in.** That defeats lever A, and DoorDash removes the item entirely rather than showing "sold out" [doc].
- **Prep time:** DoorDash has no store-level busy-mode API, and Square's busy mode excludes DoorDash [doc].
- **Racing the source of truth:** Uber warns against mixing API and Menu Maker edits [doc]. A POS menu sync can overwrite Gondola's toggles.
- **Latency:** no SLA from DoorDash/Toast/Square. Otter polls about every 5 minutes [doc]. Caps will overshoot by in-flight orders.
- **Unverified items:** Uber prep-time endpoints (third-party catalog only), Toast throttling, Chowly/Checkmate, Grubhub access, and whether DoorDash test stores need prior approval.
